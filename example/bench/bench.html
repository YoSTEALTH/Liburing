Liburing Benchmarks

Every benchmark run so far, with each run's raw numbers. Local file (in .gitignore).

Setup

  • AMD Ryzen 9 9900X (12 cores / 24 threads, 2 CCDs: CPUs 0-5 + 12-17 and 6-11 + 18-23), Linux 7.2.11
  • Zig 0.17.0, Python 3.15.0 / 3.15t, 3.14.8 / 3.14t, C liburing 2.15 (the lib/liburing submodule)
  • Liburing built with zig build develop -Drelease; C with zig cc -O2; Zig servers -OReleaseFast
  • HTTP load: tools/load.zig (from Shakti), zig-out/bin/load PORT 64 5 100: 64 threads, each one connection after another, 100 keep-alive requests per connection, for 5 seconds
  • HTTP server: one thread, pinned to CPU 2 (taskset -c 2); load on the same CCD: taskset -c 0,1,3,4,5,12,13,15,16,17 (CCD0 without CPU 2 and its SMT sibling 14)
  • net.netfilter.nf_conntrack_max = 1048576 since 2026-10-22 (was 262,144, which back-to-back runs fill up: see the note under "Every run" below)

HTTP keep-alive server, 2026-10-22

The same server (accept, recv, send the 214-byte response, recv again; close on 0 or error) written several ways: liburing_bench.c (C liburing), epoll_bench.c (C epoll), liburing_bench.py (Liburing), epoll_bench.py (select.epoll, written the same way as the Liburing one) and asyncio_bench.py (asyncio sock_recv / sock_sendall, from Shakti). Liburing arms each request three ways:

  • default: a normal SQE, as the C API does. io_uring_get_sqe(ring), the prep, sqe.user_data = ...: 3 calls and a new SQE object per request.
  • --ring: Sqe(ring), one object for the ring's lifetime. Each prep takes the ring's next free entry: the prep and sqe.user_data = ..., 2 calls and no object per request.
  • --tmpl: Sqe(no) templates. Each connection's recv and send are prepared once, in an Sqe() each, and copied into the ring with put_sqe: 1 call and no object per request (a partial send still preps the rest). liburing_bench.c uses get_sqe + prep, as the default does.

Every server reads completions as before (cqe[i], then io_uring_cq_advance). 5 runs each, all servers interleaved, -Drelease. --defer (C only here): the ring is set up with IORING_SETUP_SINGLE_ISSUER | IORING_SETUP_DEFER_TASKRUN.

An earlier run of this set had runs far below the rest (11 of 145): the kernel's conntrack table (net.netfilter.nf_conntrack_max, 262,144 then) filled up, since each run opens ~30,000 connections and a closed one stays in the table for 120 s. No server uses its whole core: req/s is limited by the round trip (64 connections, one request in flight each), so CPU per request is the better measure. Per request on 3.15: get_sqe 1.47 µs, Sqe(ring) 1.35, Sqe(no) 1.26, epoll 1.26. Sqe(ring) saves 0.12-0.17 µs/req over get_sqe, and templates another 0.09-0.15. With templates Liburing ties select.epoll on 3.15 (1.26 vs 1.26) and beats it on 3.14 (1.28 vs 1.30); free-threaded it is 0.03-0.04 behind (1.32 vs 1.28 on 3.15t, 1.33 vs 1.30 on 3.14t). Without templates it is ~0.08-0.09 µs/req behind with the GIL and ~0.18 free-threaded. In C, io_uring costs ~12% less than epoll (0.84 vs 0.95 µs).

Where the Python cost goes

  • Per request, epoll makes ~2 Python calls (recv_into, send) plus one (fd, events) tuple from poll(): 2 cheap syscalls.
  • Liburing arms each request with 3 calls (get_sqe), 2 (Sqe(ring)) or 1 (Sqe(no)), then reads cqe[i], .user_data, .res, twice per request (recv + send). Each call costs ~15-25 ns, and an object costs more.
  • asyncio is ~3.5x slower than Liburing, mostly from its own machinery (a task per connection, a future per sock_recv / sock_sendall, a new bytes per recv), not from epoll.
  • Left to try: --at (cqe.user_data_at(i) / res_at(i), no CQE objects: ~0.01-0.05 µs/req, see below), multishot recv with a provided buffer ring (one SQE for many recvs), and the free-threaded extra cost (TODO items 4, 13).

Why epoll beats Liburing in Python (but not in C)

  • Per request, epoll makes ~2 Python calls (recv_into, send) plus one (fd, events) tuple from poll(): 2 cheap syscalls.
  • Liburing makes io_uring_get_sqe, io_uring_prep_recv/_send, sqe.user_data = ..., then cqe[i], .user_data, .res, all twice (recv + send): 10+ extension calls, each creating or touching a Python object. io_uring saves the syscalls, but the Python call cost is bigger than what it saves. C has no per-call Python cost: 632k.
  • asyncio's 3.3x gap to Liburing is mostly asyncio's own machinery (a task per connection, a future per sock_recv / sock_sendall, a new bytes per recv), not epoll.
  • Ideas to put Liburing ahead: multishot recv with a provided buffer ring (one SQE for many recvs), reuse SQE objects (TODO 5), --at (no CQE objects), IORING_SETUP_SINGLE_ISSUER | IORING_SETUP_DEFER_TASKRUN (tried: --defer makes no difference here, in C or Python: within run-to-run noise).

How to run

zig build develop -Drelease
zig build load

# HTTP: start one server on CPU 2, then the load on the same CCD
taskset -c 2 zig-out/bin/liburing_bench_c 12345   # or --defer
taskset -c 2 zig-out/bin/epoll_bench_c 12345
PYTHONPATH=src taskset -c 2 python3.15 example/bench/liburing_bench.py 12345   # or --at, --defer, --tmpl, --ring
taskset -c 2 python3.15 example/bench/epoll_bench.py 12345
taskset -c 2 python3.15 example/bench/asyncio_bench.py 12345

# C servers
